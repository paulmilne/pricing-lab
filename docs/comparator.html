The Five-Model Comparator

One engagement, priced five ways

Pick a single engagement below — how many people it replaces, how much work it does, how much value it creates — then watch what the customer pays each month under every pricing model valid for your deployment tier. Nothing about the product changes between the bars. Only the commercial model changes.

Not every model is available everywhere: the CoE reference doc’s Tier-to-Model Mapping (§5.4) restricts each deployment tier to a specific subset of the five models. Change the deployment tier below and watch bars appear and disappear accordingly.

The dashed line is what the customer pays for the humans today. Anything below it is a saving you can share; anything above it needs a very good value story.

Tier-to-Model Mapping (CoE reference doc §5.4)
Tier Applicable models
Tier 1 · Internal Use M1 Per Seat (FTE-equivalent transfer price) · M2 Usage (cost recovery)
Tier 2 · Platform Services M2 Usage (API/tokens) · M3 Task · M4 Hybrid — “most flexible tier; can use any model 2–4”
Tier 3 · Digital Labor M1 Per Seat (digital employee) · M3 Task (per deliverable) · M5 Outcome (value share, mature customers only)

M4 is Tier 2-only and M5 is Tier 3-only; M1, M2 and M3 each bridge two tiers but never all three.

Note: the bar chart below deliberately omits M1 from the Tier 3 view even though the doc lists it there. M2/M3 could be reconciled onto the same footing with a calls-per-task ratio; M1’s per-seat price has no such link to task volume or business value, so showing it next to M3/M5 would suggest a false apples-to-apples comparison rather than a genuine one.

Fine-tune each model (optional)

Cost-plus inputs — the raw cost components and cost-recovery margins that build up each model’s base price. Mixed units, so read the label carefully: most are flat £/mo (M2 Tier 1’s Infra/License/Support/CoE Overhead, M4’s base fee); a few are per-unit rates that get multiplied by volume or hours inside the formula (M2 Tier 2’s unit cost and allocated overhead in £/call, M3’s rate in £/hr); the rest are percentages or multipliers, not costs at all (seat discount, both margins, M3’s complexity multiplier).

Note that Infrastructure cost only applies if the vendor runs its own infra (self-hosted compute/storage/network). If the vendor instead builds on a third-party/cloud platform, those infra costs disappear from the vendor’s own stack — the third party bears them and charges the vendor a base fee + usage instead, which belongs under License cost. Set Infrastructure to ~£0 in that case.

Risk / guardrail inputs — the per-model risk loadings (separate from the generic risk/autonomy overlay applied to M1, M2 Tier 1, and M4), plus M5’s ceiling, which guards against renegotiation risk at scale rather than capturing value:

viewof m2RiskRate   = withDescription(Inputs.range([0.05, 0.10], {value: 0.07, step: 0.01, label: "M2 T1 · risk reserve (% of cost, 5–10%)"}),
  "Buffer added on top of M2 Tier 1's base cost, per the CoE doc's 5–10% risk-reserve range.")
viewof m2T2RiskPrem = withDescription(Inputs.range([0.00, 0.20], {value: 0.01, step: 0.01, label: "M2 T2 · risk premium (£/call)"}),
  "Flat £ risk premium added per call, after the margin division — separate from the shared risk-score slider above.")
viewof m3RiskPrem   = withDescription(Inputs.range([1, 50],      {value: 5,    step: 1,    label: "M3 · risk premium per task (£)"}),
  "Flat £ risk premium added per task — separate from the shared risk-score slider above.")
viewof ceilMult     = withDescription(Inputs.range([3, 5],       {value: 4,    step: 0.5,  label: "M5 · ceiling (× floor)"}),
  "Caps M5's price at this multiple of the floor. Guards against renegotiation risk if business value scales a long way past what was priced for.")
riskPremium = (score) => {
  const pts = [[1, 0.05], [3, 0.10], [6, 0.20], [8, 0.40], [10, 1.00]];
  if (score <= 1) return 0.05;
  if (score >= 10) return 1.00;
  for (let i = 0; i < pts.length - 1; i++) {
    const [x0, y0] = pts[i], [x1, y1] = pts[i + 1];
    if (score >= x0 && score <= x1) return y0 + (y1 - y0) * (score - x0) / (x1 - x0);
  }
}
autonomyMod = (lvl) => (lvl === "L4" ? 1.20 : lvl === "L5" ? 1.40 : 1.00);
overlay = (base) => base * (1 + riskPremium(riskScore)) * autonomyMod(autonomy);

humanMonthly = fteCount * fteCost / 12;

// Tier-to-Model Mapping (CoE reference doc §5.4) — which of the five models
// are actually offered under each deployment tier.
// Per §5.4, Tier 3 officially includes M1 (per-seat "digital employee") too.
// It's deliberately left out of the comparator's bar chart: unlike M2/M3
// (linked via calls-per-task), M1's price has no connection to volume or
// business value at all — it answers a different question (headcount, not
// task/outcome volume), so plotting it next to M3/M5 would imply a false
// apples-to-apples comparison. M1 stays available as a valid Tier 3 option
// elsewhere (e.g. the Model Selector); it's just not plotted here.
TIER_MODELS = ({
  "Tier 1 · Internal Use":        ["M1 Per Seat", "M2 Usage"],
  "Tier 2 · Platform Services":   ["M2 Usage", "M3 Task", "M4 Hybrid"],
  "Tier 3 · Digital Labor":       ["M3 Task", "M5 Outcome"],
})
activeModels = TIER_MODELS[dealTier];

// M2's formula depends on which tier it's playing in: Tier 1 = internal
// cost recovery (flat), Tier 2 = platform usage (per unit). It never
// appears in Tier 3, so this only matters when M2 is actually shown.
isM2Tier1 = dealTier.startsWith("Tier 1");

// The Tier 1 cost-recovery breakdown (Infrastructure + License + Support +
// CoE Overhead, plus a risk reserve on top) is the only real "cost of goods"
// here — the same product runs underneath every bar, so the vendor's cost to
// deliver it does not change with the commercial model chosen.
m2BaseCost    = m2Infra + m2License + m2Support + m2CoEOverhead;
m2RiskReserve = m2BaseCost * m2RiskRate;
vendorCost    = m2BaseCost + m2RiskReserve;

// M3's compute cost, modelled as a log-normal token-cost distribution — same
// approach as token-distribution.qmd. Z90 is the standard normal's 90th
// percentile (fixed constant), used instead of a general quantile function
// since we only ever need the P90 point on this curve.
Z90 = 1.2816
m3TokenSigma   = Math.sqrt(Math.log(1 + m3TokenCoV ** 2))
m3TokenMuC     = Math.log(m3MedianTokens) + Math.log(m3TokenRate / 1000)
m3ComputeCostMean = Math.exp(m3TokenMuC + m3TokenSigma ** 2 / 2)
m3ComputeCostP90  = Math.exp(m3TokenMuC + Z90 * m3TokenSigma)

// M2 Tier 2's "unit cost" (infra + license per call) is the same kind of
// token cost, same log-normal treatment — just at per-call rather than
// per-task scale.
m2TokenSigma   = Math.sqrt(Math.log(1 + m2TokenCoV ** 2))
m2TokenMuC     = Math.log(m2MedianTokens) + Math.log(m2TokenRate / 1000)
m2ComputeCostMean = Math.exp(m2TokenMuC + m2TokenSigma ** 2 / 2)
m2ComputeCostP90  = Math.exp(m2TokenMuC + Z90 * m2TokenSigma)

// Exposed at top level (not just inside the `prices` cell below) so the
// sensitivity tables further down the page can reference them too.
m3TaskPrice = (m3Hours * m3Rate) * m3Complexity + m3RiskPrem
m2UnitPrice = (m2ComputeCostMean + m2AllocOverhead) / (1 - m2T2Margin) + m2T2RiskPrem
m2EffectiveCalls = volume * m2CallsPerTask

// Deep-links into token-distribution.qmd, pre-filled with this page's
// current M2/M3 token settings via query string, so the "explore this in
// depth" links actually open on the same scenario instead of that page's
// own hardcoded defaults. `markup` is back-solved as the % the quoted
// price sits above the MEAN cost, matching that app's own "markup" slider
// semantics; `volume` is clamped to that app's 100–5000 slider range.
tokenDistLink = (median, cv, rate, vol, price, meanCost) => {
  const markup = Math.max(0, Math.min(50, 5 * Math.round(
    (meanCost > 0 ? (price / meanCost - 1) * 100 : 0) / 5
  )));
  const params = new URLSearchParams({
    median: Math.round(median),
    cv: cv,
    rate: rate,
    volume: Math.max(100, Math.min(5000, Math.round(vol))),
    markup: markup,
  });
  return `token-distribution.qmd?${params}`;
}
m3TokenDistHref = tokenDistLink(m3MedianTokens, m3TokenCoV, m3TokenRate, volume, m3TaskPrice, m3ComputeCostMean)
m2TokenDistHref = tokenDistLink(m2MedianTokens, m2TokenCoV, m2TokenRate, m2EffectiveCalls, m2UnitPrice, m2ComputeCostMean)
m3TokenDistLink = html`<a href="${m3TokenDistHref}">Token Distribution &amp; the P90 Floor</a>`
m2TokenDistLink = html`<a href="${m2TokenDistHref}">Token Distribution &amp; the P90 Floor</a>`

// A per-model breakdown of *why* the cost line is what it is — each model's
// cost comes from a genuinely different formula (see the Causal Map), so
// this can't be one fixed set of line items; it switches on which model is
// being hovered.
costBreakdown = (model) => {
  if (model === "M2 Usage" && !isM2Tier1) {
    return [
      ["P90 compute cost", `${gbpUnit(m2ComputeCostP90)}/call × ${m2EffectiveCalls.toLocaleString()} calls`, m2ComputeCostP90 * m2EffectiveCalls],
      ["Allocated overhead", `${gbpUnit(m2AllocOverhead)}/call × ${m2EffectiveCalls.toLocaleString()} calls`, m2AllocOverhead * m2EffectiveCalls],
    ];
  }
  if (model === "M3 Task") {
    return [
      ["P90 compute cost", `${gbpUnit(m3ComputeCostP90)}/task × ${volume.toLocaleString()} tasks`, m3ComputeCostP90 * volume],
    ];
  }
  // M1, M2 Tier 1, M4, M5 all share the Tier 1 cost-recovery breakdown.
  return [
    ["Infrastructure", "compute + storage + network", m2Infra],
    ["License", "vendor fees per agent/API call", m2License],
    ["Support", "CoE FTE allocation", m2Support],
    ["CoE overhead", "governance, training, monitoring", m2CoEOverhead],
    ["Risk reserve", `${(m2RiskRate * 100).toFixed(0)}% of the above`, m2RiskReserve],
  ];
}
// Plot's tip truncates each channel to a fixed character width regardless
// of content, so one long joined string (or embedded newlines) doesn't
// work — split into several short, fixed-key rows instead. Pack two cost
// items per row where there are enough to make that worthwhile.
costBreakdownRows = (model) => {
  const items = costBreakdown(model).map(([label, , amount]) => `${label} ${gbp(amount)}`);
  while (items.length < 5) items.push("");
  return items;
}

prices = {
  const m1 = overlay(fteCount * (fteCost / 12) * seatDiscount);

  // M2 · Tier 1: internal cost-recovery, flat regardless of volume. Takes the
  // generic risk/autonomy overlay since the formula has no risk term of its own.
  const m2Tier1Price = overlay(vendorCost / (1 - m2Margin));

  // M2 · Tier 2: platform usage, priced and billed per unit, scaling with
  // *calls*, not tasks — volume × callsPerTask converts the shared "tasks
  // delivered" input into the same workload M3 is pricing, instead of
  // treating 1,000 calls and 1,000 tasks as equivalent amounts of work.
  // Skips the generic overlay — like M3, its own per-unit risk premium
  // already prices that in, so applying both would double-count it. The
  // quoted price builds off the MEAN token cost (m2UnitPrice, computed at
  // top level — standard cost-plus practice), but the true cost basis below
  // uses the P90 tail cost instead, same tail-risk lesson as M3.
  const m2Tier2Price = m2EffectiveCalls * m2UnitPrice;
  const m2Tier2Cost  = (m2ComputeCostP90 + m2AllocOverhead) * m2EffectiveCalls;

  const m2 = isM2Tier1 ? m2Tier1Price : m2Tier2Price;
  const m2Cost = isM2Tier1 ? vendorCost : m2Tier2Cost;

  // M3 follows the CoE reference doc's task-pricing formula directly rather
  // than the overlay: Task Price = (Hours × Rate) × Complexity + Risk Premium.
  // It skips the generic risk/autonomy overlay because its own risk premium
  // term already prices that in per task — applying both would double-count it.
  const m3 = volume * m3TaskPrice;
  const m3Cost = m3ComputeCostP90 * volume;

  const m4 = overlay(m4BaseFee + value * m4Share);

  // M5 has its own floor/ceiling guardrails rather than the overlay
  const m4BaseOverlaid = overlay(m4BaseFee);
  const floor   = 0.8 * m4BaseOverlaid;
  const ceiling = ceilMult * floor;
  const m5raw   = value * m5Share;
  const m5      = Math.max(floor, Math.min(ceiling, m5raw));
  const m5bind  = m5raw <= floor ? "floor binds" : m5raw >= ceiling ? "ceiling binds" : "share applies";

  const withProfit = (model, price, note, cost = vendorCost) => ({
    model, price, note,
    cost,
    profit: price - cost,
    marginPct: price > 0 ? (price - cost) / price : 0,
  });

  const all = [
    withProfit("M1 Per Seat", m1, `${(seatDiscount*100).toFixed(0)}% of human rate`),
    withProfit("M2 Usage",    m2,
      isM2Tier1
        ? `cost recovery @ ${(m2Margin*100).toFixed(0)}% margin`
        : `${m2EffectiveCalls.toLocaleString()} calls × ${gbpUnit(m2UnitPrice)}/call`,
      m2Cost),
    withProfit("M3 Task",     m3, `${volume.toLocaleString()} tasks × ${gbp(m3TaskPrice)}/task`, m3Cost),
    withProfit("M4 Hybrid",   m4, `base + ${(m4Share*100).toFixed(1)}% of value`),
    withProfit("M5 Outcome",  m5, m5bind),
  ];

  // Only show the models this deployment tier actually permits (CoE §5.4).
  return all.filter(d => activeModels.includes(d.model));
}

The margin % printed above each bar is a realized margin — (price − cost) ÷ price, using the cost line shown when you hover — not the margin you set on a slider. The two usually differ: M2 Tier 1’s risk/autonomy overlay stacks pure profit on top of its cost-recovery margin (so the bar reads higher than the slider), while M2 Tier 2’s price is quoted off the mean token cost but costed here against the fatter P90 tail (so the bar reads lower than the target). See “How vendor cost is estimated here” and the sensitivity callouts below for why.

How “vendor cost” is estimated here

The vendor’s cost to serve is built from the CoE reference doc’s Tier 1 cost-recovery breakdown: Infrastructure + License + Support + CoE Overhead, plus a Risk Reserve (5–10% of that base cost). This total is the same figure across M1, M2 Tier 1, M4 and M5, because the underlying agent and workload don’t change — only the commercial wrapper around them. Any model-specific base/platform fee (M4) is assumed to cover its own overhead and is left out of this cost line, so profit here is a gross margin on cost of goods, not a fully-loaded operating margin.

M2 Tier 2 and M3 are the two exceptions, each for the same underlying reason: their price scales with volume, but the Tier 1 monthly breakdown doesn’t, so comparing them produces a nonsensical or exaggerated margin. Both are also priced and costed off AI compute — i.e. tokens — rather than the Tier 1 infra breakdown, so both use their own token-based cost line instead, costed at the P90 tail rather than the mean (see the two callouts below).

How each bar is calculated

The risk and autonomy settings apply on top of M1, M2 and M4 as a single overlay — this is the framework’s “apply the premium on top of the model price” rule:

\[\text{overlay}(x) = x \times \big(1 + \text{risk premium}\big) \times \text{autonomy modifier}\]

where the risk premium runs from +5% (score 1) to +100% (score 10), and the autonomy modifier is ×1.00 up to L3, ×1.20 at L4, and ×1.40 at L5.

// \texttip (MathJax's own tooltip) renders through the browser's native
// `title` attribute — slow to appear (OS-level hover delay) and unstyled.
// Swapped for tippy.js instead, which Quarto already loads on every page for
// footnote/xref popovers (window.tippy), so no new dependency. Each term is
// tagged with \cssId (MathJax's "html" extension, autoloaded by default) so
// it can be found in the typeset DOM afterwards and handed its own tippy
// instance, built from the CURRENT slider values — rebuilt on every slider
// change since this cell depends on those reactive inputs.
howEachBarTex = {

  const ceilingVal = ceilMult * floorVal;

    const id = `tip-term-${tipCounter++}`;
    tipMap.set(id, tipText);

  };

M2 has two personalities, and the deployment tier picks between them automatically. In Tier 1 it’s a flat internal cost-recovery number (no risk term of its own, so it does take the overlay) — notice it doesn’t move at all when you change the volume slider. In Tier 2 it’s a true per-unit usage price that scales with volume, and — like M3 — it carries its own risk premium, so it skips the generic overlay to avoid double-counting risk. M2 isn’t offered at all in Tier 3, so its fine-tune sliders simply have no bar to affect there.

Where Tier 2’s “unit cost” comes from. It isn’t a flat guess — it’s a per-call AI compute cost, modelled the same way as M3’s token cost (and ): tokens per call are log-normal, set by the median tokens/call and token CoV sliders, and converted to £ via the token rate slider:

\[\mu = \ln(\text{median tokens}) + \ln\!\left(\frac{\text{token rate}}{1000}\right), \qquad \sigma = \sqrt{\ln\!\left(1 + \text{CoV}^2\right)}\]

\[\cssId{tip-unit-cost-mean-def}{\class{tip-term}{\text{unit cost}_{\text{mean}}}} = \exp\!\left(\mu + \frac{\sigma^2}{2}\right), \qquad \cssId{tip-unit-cost-p90-def}{\class{tip-term}{\text{unit cost}_{\text{P90}}}} = \exp\!\left(\mu + z_{0.90}\,\sigma\right)\]

The quoted price above uses \(\cssId{tip-unit-cost-mean-ref}{\class{tip-term}{\text{unit cost}_{\text{mean}}}}\) — standard cost-plus practice, since you can’t quote a customer a percentile. The vendor cost used for the profit/margin chart instead uses \(\cssId{tip-unit-cost-p90-ref}{\class{tip-term}{\text{unit cost}_{\text{P90}}}}\), so the displayed margin reflects the fat tail of expensive calls rather than an optimistic average (see the sensitivity callout above for how much the two diverge as CoV rises).

  }
  window.__unitCostProseTips = instances;
}

M3 follows the same logic as M2 Tier 2: it’s the CoE reference doc’s task-pricing formula directly, with its own per-task risk premium, rather than the generic risk/autonomy overlay used by M1, M4 and M2 Tier 1. Applying the overlay and a per-unit/per-task risk premium would price risk twice.

M5 uses guardrails instead of the overlay: the floor is 80% of the (overlaid) M4 base fee — protecting your cost recovery — and the ceiling is a multiple of that floor, capping the customer’s exposure. Push the business value slider up and watch M5 climb off its floor, then slam into its ceiling: that is the whole story of outcome-based pricing in one slider.
